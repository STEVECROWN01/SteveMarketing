QUATRE CAUSES RACINE, QUATRE CORRECTIFS :

F1 — TEXTE DU HERO À OPACITY: 0 DANS LE HTML SSR (accueil, LCP 1256 → 220 ms). Les révélations au scroll (Reveal/RevealText) servent leur état initial masqué : le paragraphe du hero — élément LCP de l'accueil — n'était peint qu'après chargement JS + hydratation + retour de l'IntersectionObserver + délai + transition, mesuré 948-968 ms pour un FCP à 168 ms. Correctif : nouveau mode « aboveFold » de Reveal/RevealText — animations CSS .reveal-fold--up / .reveal-fold-word (globals.css) aux courbes, durées et décalages IDENTIQUES aux transitions JS, mais démarrées au premier rendu sans JavaScript — la même mécanique que la chorégraphie du bloc visuel (.hero-anim-*, 15/11) ; ironie : seul le TEXTE du hero attendait l'hydratation. La cascade étoiles → titre → description → CTA → réassurance est conservée, elle démarre à la première frame (pendant que la plaque surgit) au lieu d'après l'hydratation. Le reste du site (tout ce qui est sous le pli) garde les révélations au scroll, inchangé.

F1-bis — LE FONDU REND LE LCP AVEUGLE (découverte technique centrale du volet). Une fois le texte animé en CSS, il était VISIBLE à ~200 ms mais l'API LCP continuait de le rapporter à 1584 ms (trace scripts/diag-hero.js : opacité 0 → 0,53 à t=200 → 1 à t=700, candidate à 1584). Explication : les animations d'opacité sont pilotées par le compositeur — le navigateur ne ré-émet AUCUNE paint pendant le fondu, et l'API LCP n'enregistre l'élément qu'à la prochaine paint forcée (ici le rééquilibrage vertical de la description à l'hydratation + 1150 ms). Correctif : l'ÉLÉMENT LCP lui-même (p.hero-desc) reçoit la variante aboveFold="rise" — translation seule (translateY 28px), SANS fondu : peint à la première frame, candidate dès le FCP ; LCP = FCP. Le fondu reste sur les éléments voisins (étoiles, mots du titre, CTA, réassurance) — tous plus petits, ils ne peuvent pas lui disputer le statut d'élément LCP (vérifié aux deux viewports).

F2 — ANIMATION DE SORTIE POUR UN CONTENU JAMAIS VU (pages profondes, −320 ms). Au chargement direct d'un lien profond, le serveur sert le HTML de l'ACCUEIL (il ne voit jamais le fragment) ; l'hydratation résout la vraie page et AnimatePresence mode="wait" attendait pourtant l'animation de SORTIE de ce contenu intermédiaire (320 ms) avant de monter la page cible — 320 ms perdues à fondre un écran que le visiteur n'avait pas eu le temps de voir. Correctif (page.tsx) : la clé « boot » → « app » REMONTE AnimatePresence à la première résolution d'une page ≠ accueil — démontage immédiat, montage immédiat (initial={false}) ; les navigations suivantes retrouvent le comportement normal (sortie puis entrée), clé stable.

F3 — ÉCRAN D'AMORÇAGE DES LIENS PROFONDS (attribut seul, zéro insertion DOM). Avant ce volet, le visiteur d'un lien partagé voyait défiler l'accueil (hero, images) puis un fondu puis un spinner avant SA page. Le script inline (layout.tsx, rendu au plus tôt du corps du HTML) pose data-boot="deep" sur <html> quand le fragment désigne une page profonde : le contenu intermédiaire est masqué (visibility: hidden — ne génère AUCUNE candidate LCP, vérifié) et un écran d'amorçage (voile #1c1c1c + spinner, même esthétique que l'attente de morceau) couvre l'écran — TOUT le visuel est porté par des règles CSS statiques de globals.css. NettoyageAmorcage (page.tsx) lève l'écran au montage du main de la page demandée (branché aussi sur la branche admin) ; filet de sécurité à 6 s (retrait de l'attribut) pour ne jamais laisser un visiteur sur un écran figé si l'application ne prend pas la main. DEUX FAUSSES PISTES documentées au passage : (a) l'écran inséré comme nœud DOM cassait l'hydratation à la RACINE (React hydrate <html>/<body> eux-mêmes dans l'App Router → re-rendu client complet, LCP mesuré 1284-2524 ms) — l'attribut seul suit le modèle éprouvé de la classe .hoverable ; (b) next/script strategy="beforeInteractive" ne s'exécute qu'au boot du runtime — vérifié : sérialisé dans le payload Flight (self.__next_f.push), mesuré à 223 ms, APRÈS le FCP (180 ms) — d'où le script inline brut, rendu à sa place dans le HTML comme le JSON-LD. Au passage : le commentaire du script detect-hoverable est corrigé (il prétendait s'exécuter « avant l'hydratation »).

F4 — FONDU DE RÉVÉLATION SUR CONTENU DÉJÀ VISIBLE AU MONTAGE (pages profondes, −700 ms). Après F2+F3, le contenu Méthode était RENDU à ~670 ms (opacité finale, main visible) mais sa candidate LCP n'arrivait qu'à ~1476 ms : la transition d'opacité de sa révélation (700 ms) est pilotée par le compositeur — même aveuglement que F1-bis, mais côté destination. Correctif (Reveal.tsx, useInView) : sur une page ouverte par LIEN PROFOND (window.__amorcageProfond, posé par le script d'amorçage), un élément dont la PREMIÈRE intersection arrive sans aucun défilement n'a rien à « révéler » — son opacité bascule INSTANTANÉMENT (transition opacity 0ms) et seule la translation reste animée ; la candidate LCP est enregistrée dès la paint de bascule (~50 ms après le montage). Comportement STRICTEMENT inchangé dans tous les autres cas : navigation interne (fondu conservé — vérifié visuellement), défilement descendant (fondu + translation), remontée (apparition immédiate), prefers-reduced-motion (statique).

LEÇONS DE MESURE (scripts/sonde-lcp-2026-11-19.js, réutilisables) : (1) le volet 3 lisait le LCP trop tôt — son « 284 ms » sur #/methode mobile était le logo du header avant la page ; la sonde du volet 7 attend la STABILISATION (2 s sans nouvelle candidate, plafond 12 s) et rapporte TOUTES les candidates avec élément ; (2) après une passe sur /, un goto vers /#/methode n'est qu'une navigation PAR FRAGMENT dans le MÊME document — pas de rechargement, le buffer LCP garde les candidates de la page précédente et le script d'amorçage ne s'exécute pas : la sonde force un document neuf via about:blank avant chaque passe ; (3) une candidate LCP n'est émise que si elle est PLUS GRANDE que la précédente — un artefact précoce (hero d'accueil transitoire, 51 796 px²) masquait le vrai contenu (17 840 px²) ; (4) les animations d'opacité — CSS OU transitions — ne génèrent aucune repaint : un LCP « au fondu près » est mesuré à la prochaine paint forcée, pas à l'apparition visuelle ; (5) pièges d'instrumentation rencontrés et corrigés dans les scripts : NodeList n'a pas de .slice, p.mt-2.5 est un sélecteur CSS invalide (les classes ne peuvent pas commencer par un chiffre — utiliser [class~="mt-2.5"]), documentElement n'existe pas encore au moment des scripts d'initialisation (réessai), et les chaînes requestAnimationFrame ne tirent pas de façon fiable avant la première paint (échantillonner par setTimeout).
